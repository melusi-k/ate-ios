## 1. User value

One Ate account, every device: a user who loses or replaces their iPhone, or cooks from two devices, gets their Food Journal and nutrition goals back on sign-in instead of starting empty. Insight states stay on the roadmap (see the dormancy note in section 4 and the follow-ups). Recipes and shopping lists already sync this way; the rest of the user's data was still trapped per-device, and the Journal even promised "Saved only on this iPhone".

## 2. Scope

| Family | Kind | Identity | Payload | LWW stamp |
| --- | --- | --- | --- | --- |
| Food Journal entries (meals + reflections) | `journal` | `JournalEntry.id` (UUID string) | `JournalEntrySyncPayload`: every `JournalEntry` field + the one-to-one meal payload, recipe snapshots as stored raw JSON | `editedAt ?? createdAt`, whole ms |
| Insight lifecycle states (seen / dismissed / snoozed / resolved / expired, evidence fingerprint) - **DORMANT this slice** | `insight` | insight id | `InsightLifecycleRecord` verbatim | `record.updatedAt`, ms |
| Nutrition goals | `goals` | constant `current` | `DailyNutritionGoals` verbatim | byte-change detection against last synced payload, stamped now |

**Deliberately out (phase 1), with the reason:**

- **Journal media bytes.** `mediaFileNames` sync as references; the files stay on the capturing device (rows are jsonb with a 200 KB cap; media needs storage buckets + a lifecycle policy - separate design).
- **Health data.** None is synced. `JournalEntry.stateRaw` is Ate's own HealthState label, not HealthKit payloads; HealthKit samples never leave HealthKitService.
- **App settings, timer prefs, cooking history, drafts, widget state.** Syncable later under the same pattern; each needs its own conflict story (settings especially) and is not in the parked scope.
- **Legacy food diary.** Already migrated into the journal container (#245); it syncs as `journal` meal rows.

## 3. Backend shape

Reuse `public.user_recipes` (one RLS surface, one LWW clock `updated_at` bigint, one tombstone model, `clear_account_data` already deletes every kind for the owner). The only schema change is widening the `kind` CHECK allow-list to `('recipe','shopping','journal','insight','goals')` - additive, no table rewrite, no policy change. Row cap (200 KB) is ample: a long reflection is single-digit KB.

Writes go through the generation-fenced RPC contract (`account_data_snapshot`, `put_user_recipe`) that #528 deployed, and ONLY through the fenced writer of the unified graph: `FencedUserDataSyncTransport` wraps `GenerationFencedSync` plus the persisted generation receipt. One pull capture authorizes exactly one batch push (single-use even on failure), with session, writer lease and receipt re-proved around every await.

**Cycle exclusion (Builder review):** the staged recipe/shopping cycle's busy flag lives on its own transport, so a separate family busy flag would NOT stop the two cycles interleaving. Both transports instead share ONE `SyncCycleGate` constructed by the application owner: each transport's `cycle(session:work:)` acquires the gate around its whole cycle, and a round arriving mid-cycle fails `cycleInProgress` and defers to the next sync. `gate.replace()` recovers a cycle abandoned by an app kill: the orphaned token fails `validate` as `superseded` instead of writing under a stale capture. The gate lives on the owner, never on the receipt store, so the fenced reset path is never blocked by it. The host that builds the unified graph (the #532 application owner) binds the transport via `AppStore.userDataSyncTransport`; that binding is the one seam this slice needs from the #532 sync-core. On the legacy graph (`foodJournalRuntime == nil`, or the seam unbound) families stay local-only - no unfenced RPC writer beside the admitted one. If the RPC contract is absent (old backend), the family round skips cleanly (`contractMissing`).

**Publication order inside one cycle (Reviewer):**

1. **Validate the whole snapshot strictly** (`RemoteSnapshotValidator`): every family row's wire id is non-empty and unique per kind, stamps are sane, and every live payload decodes with strict identity (payload id == wire id) and structure - kind/meal consistency, known enums (`JournalEntryKind`, `HealthState`, `JournalEntrySource`, `NutritionMeal`, `NutritionEntrySource`), day-key shape, positive quantity/servings, non-negative finite nutrients, safe media file names, the fixed `goals` row id. ANY violation rejects the round (`remoteRejected`) before any local write or upload: no partial apply.
2. **Stage every family**: export local, plan LWW, decode remote winners - no local mutation. Staged proposals are discarded on failure.
3. **Authorized batch upload first** (single-use push authorized by the snapshot capture).
4. **Revalidate** gate + session + generation (`revalidate` closure from the transport): a reset or account change mid-cycle abandons publication even after a successful upload.
5. **One journaled commit** (`FamilySyncCommitJournal`, the #532 redo-journal discipline): the second local read runs inside the admitted boundary BEFORE anything is recorded; then a durable, checksummed, receipt-bound intent (complete family metadata after-image + per-family before/after images) is installed atomically; every store is driven to the recorded target idempotently; the metadata authority is durable before the defaults projection; the intent is retired last. A refused or revoked writer leaves content AND metadata unchanged; an interrupted commit is completed by replay at the next round (never rolled back); a failed upload publishes nothing locally - the next round re-pushes the same rows (LWW makes that idempotent) and re-stages the same remote winners.

## 4. Conflict semantics

- **Last-write-wins per (kind, id)** with whole-millisecond stamps - the exact `SyncMerge` engine recipes/shopping already use, reused through `UserDataSyncPlanner` (pure, unit-tested).
- **Deletes propagate as tombstones.** Local deletion is detected by diffing the live export against the persisted previously-synced stamps (`localWithDeletes`): an entry the device synced before that is gone locally becomes a tombstone stamped now and pushes as `deleted=true`. A re-sync is a no-op (rounded-ms comparison, same as recipes).
- **Validate, stage, upload, then ONE journaled commit.** The whole snapshot is strictly validated first (identity, shape, wire-stamp/payload-version agreement); every family is then staged (plan + decode + expected-image, no mutation); the authorized upload runs; gate/session/generation are re-proved; and only then does the commit publish. Inside the admitted boundary the commit first re-reads every family input and refuses if it changed during the upload (an edit/delete/goals change is never overwritten by a staged remote winner; the next round re-stages from the new content). Stamps never persist without their content, and content never publishes from a round whose upload did not complete.
- **Durable REDO journal, never rollback** (`FamilySyncCommitJournal`, a direct port of #532's `RecipeShoppingSyncCommitJournal` discipline to the family stores). Before the first mutation the commit records a versioned, checksummed intent - atomic temp+fsync+rename+dir-sync+readback install - holding the receipt (owner + generation), the COMPLETE family metadata after-image, and per driven family BOTH the admitted before-image and the complete target after-image. Every apply is an idempotent full-scope drive to the after-image, and replay PREFLIGHTS every driven family plus the metadata ownership BEFORE any write: a foreign or changed family refuses the whole replay with nothing mutated. Metadata lands as a durable authority file and UserDefaults is only its projection (family fields merged into the current metadata - recipe/shopping fields are never projected from authority, so replay can never roll back a later recipe/shopping stamp; corrupt existing `ate.sync.v1` bytes or a non-nil foreign `userID` refuse the common projection without being overwritten (including bare-authority recovery and reset)). An interrupted commit is COMPLETED by replay at the next round: content already at the after-image is left, content still at the before-image is driven forward, ANY other content (an edit after a crash, foreign rows) refuses the replay and preserves both. Replay also re-proves the CURRENT session + live generation receipt: a pending intent from another account or an old epoch refuses fail-closed until the reset composition erases the directory (`clearAllComponent` is the inventory hook). A corrupt/ambiguous intent or authority blocks the round and preserves the evidence; raw absence is a no-op.
- **Goals durability before retirement.** `FileNutritionGoalsStorage.write(.atomic)` alone is insufficient. `FamilySyncGoalsDurability` seals the exact repository target under the admitted writer: temp write, file `fsync` + `F_FULLFSYNC`, rename, parent-directory `fsync`, readback. An empty target is an idempotent unlink plus parent sync and absence readback. The round includes the complete goals target even with no local delta (push-only rounds must seal too), and replay seals an already-applied target again. An unavailable durability step or non-file storage refuses retirement and preserves the intent. The file parent must already be provisioned by the host; no fallback directory is chosen. These mechanics have injected failure coverage, but native execution and OS power-loss validation are unrun.
- **Insight states: DORMANT this slice (Reviewer split).** Commit AND replay reject non-nil insight before/after images by default; only an explicit debug-test fixture permits them, and release builds reject that override. The round produces no insight images. The reason is that `InsightLifecycleStore` keeps content in UserDefaults, which is not crash-durable the way the journal's SwiftData store and the goals file store are - and no post-commit repair layer closes that gap: a repair image cannot distinguish a lost volatile apply from a deliberate local removal (deletions leave no `updatedAt`), so it would either resurrect removed states or revert ordinary edits. The round therefore skips the insight family entirely (wire kinds, migration allow-list and planner support stay); insight sync returns with a crash-durable insight store (follow-up below), not with another partial fix.
- **Per-family confirmation scope.** `SyncMeta` carries `journalScope`/`insightScope`/`goalsScope` (owner + generation) instead of one aggregate scope: a family that stages successfully confirms under the round's scope; a family that FAILED keeps its carried-over older scope and stamps, so the commit never promotes a failed family's stale confirmations into the new owner/epoch. An owner/epoch change clears all three scopes with the family stamps (`clearFamilySyncStateForNewEpoch`).
- **Account switch.** Family stamps/tombstones live in `SyncMeta` and are reset by the existing account-switch path together with recipe/shopping stamps, so account A's rows never merge or tombstone into account B. Per-record confirmation is additionally bound to an `AccountDataScope` (owner + generation) persisted at commit: after switching from A to B - even before any reset runs - A's stamps never confirm records under B, and a generation advance (reset elsewhere) breaks confirmation until the next successful round. Journal content that predates sync belongs to the device owner and begins syncing under the account they sign into - same semantics as a first-ever recipe sync.
- **Generation fencing.** `staleGeneration` mid-round aborts the whole round; the next sync re-snapshots. No partial epoch is ever written. On a confirmed generation change the round clears every family stamp, tombstone, synced-payload marker and the persisted scope, so old-epoch state can neither confirm nor re-plan anything.

## 5. Privacy, retention, deletion, export

- **Copy honesty, per record.** The aggregate round status never speaks for a single record. `AppStore.journalRecordSyncState(id:createdAt:editedAt:)` separates "ever uploaded" from "current version confirmed": it returns `.confirmed` only when the server holds THAT record's current version under the CURRENT account scope (its stamp persisted with a successful round's commit AND the persisted `AccountDataScope` still matches the session owner and the live generation receipt), `.pending` while the current version is only on the iPhone and upload can run (new, edited, re-scoped, not yet uploaded), `.cloudCopyOnly(currentVersion:)` when the account holds a version of the record but no upload can run right now (sync off, signed out, seam unbound, backend refusing) - `currentVersion: true` when it holds THIS version, `false` when it holds an EARLIER one, with copy that says which - and `.localOnly` only when the server holds nothing of that record at all. Composers say "queued to sync" (a record being written has not uploaded); the entry detail shows the record's own state. `userDataSyncStatus` and the backend-unavailable flag reset on any session/account change, so one account's round state never leaks into another's copy; the per-record cloud-copy fact survives sign-out because the server copy does. While the backend is unmigrated, never-synced records report local-only; the copy never claims sync that is not happening.
- **Clear All.** Server-side, `clear_account_data` deletes every kind for the owner, so a signed-in Clear All wipes journal/insight/goals rows with the rest. Local wipe lists were already audited ("sync metadata/tombstones deliberately NOT on these lists"); no change in this slice. Reviewer: confirm the reset-composition tests still hold with the new kinds present in a snapshot.
- **Export/restore.** `AteDataArchive` is unchanged: export stays a local device artifact. Cloud-synced data re-arrives by signing in; export is the no-account path. Diary entries inside the archive still restore through the existing import, and sync then treats them as ordinary local rows.
- **No new data leaves the device beyond what the families contain.** No titles or content in logs: push/apply paths log counts only (BetaQA already does this for recipes).

## 6. Rollout and failure behavior

- **Default ON** (`AppConfig.userDataSyncEnabled`) as a product preference; OFF switches: `-qaUserDataSyncOff` launch argument or Info.plist `AteUserDataSync = "off"`. The preference ships client behavior only - it does not grant production changes: the migration stays file-only until the owner explicitly applies it. Effective ONLY when the unified (fenced) graph is active and the host seam is bound; the legacy graph keeps families local-only (no unfenced family writes).
- **Blocking bound.** `syncNow` AWAITS the family round after `syncState` is already `.synced`, so a slow family round extends `syncNow`'s completion by one snapshot + one batch upload behind the shared gate. Family FAILURES never change `syncState` or block Library/Cook; the latency of one fenced round is the only cost recipe/shopping callers observe.
- **Backend not migrated yet** (the expected state until Melusi says yes to the SQL): PostgREST rejects the new kinds with 23514, or the RPC contract is missing entirely. Both classify as `familyUnavailable`: the round skips, `userDataSyncStatus` records it, and nothing is written, deleted or shown as synced. Recipe/shopping sync, Library and Cook are structurally untouched (family sync runs after `syncState` is already `.synced`, in its own do/catch per family).
- **UI tests** skip family sync entirely (`isUITesting`), keeping the existing MockSync surface stable.
- **Status surface:** `AppStore.userDataSyncStatus` (`.synced` / `.unavailable(detail)`) is published for a future Settings row; no UI surfaces it yet besides the Journal privacy line.

## 7. Failure modes

| Failure | Behavior |
| --- | --- |
| `user_recipes` kind CHECK not widened (23514) | Family round skips; retried every sync; local data intact |
| RPC contract missing (404/PGRST202) | All families skip at snapshot; local-only |
| Session expired / unauthorized | Surfaced as unavailable; existing `expireSession` path owns sign-out |
| Stale generation (reset elsewhere) | Round aborts before the batch push; next sync re-snapshots fresh |
| Malformed / inconsistent remote row | Whole round rejected (`remoteRejected`) before any local write or upload; no partial apply |
| Upload failed (HTTP, 23514) | Staged proposals discarded; nothing published locally; stamps unchanged; next round re-plans (idempotent) |
| Reset / account change at pre-commit revalidation | Publication abandoned even after a successful upload; local content untouched |
| Local edit / delete / insight / goals change during the upload | The commit's second local read refuses publication; the new local content stands; stamps unchanged; next round re-stages from it |
| Crash/throw mid-commit (any store apply, metadata write, intent retire) | The recorded intent stays durable; the NEXT round's replay completes the same target idempotently - no rollback ever runs |
| Ordinary edit lands after a crash, before replay | Replay refuses (content no longer matches the admitted before-image); the edit AND the intent are preserved; the round reports unavailable until the reset composition resolves it |
| Pending intent from another account / old generation | Replay refuses fail-closed (`ownerChanged`); nothing is published under the wrong owner or epoch; the reset composition (`clearAllComponent`) owns erasure |
| Foreign content in a LATER family (journal still at before-image) | Preflight refuses the replay BEFORE any write; every family is preserved |
| Corrupt / ambiguous intent or authority (bad checksum, both pending+temp, unreadable) | The round BLOCKS before any staging; the evidence is preserved byte-for-byte; raw absence is a no-op |
| Corrupt existing `ate.sync.v1` (undecodable / non-Data) | The projection refuses WITHOUT writing; the raw bytes are preserved; the intent survives for replay after the metadata is repaired |
| Defaults projection lost (defaults wiped) | The durable authority re-projects the family metadata at the next round |
| Writer refused / revoked at the admitted commit | Local content AND metadata unchanged; honest `unavailable` status |
| Cycle gate busy (recipe/shopping cycle in flight, or vice versa) | Round deferred with `userDataSyncStatus = unavailable("another account-data sync cycle is active")`; retried on the next sync trigger |
| Cycle superseded (orphaned by `replace()` after an app kill) | Aborts as `sync cycle was superseded by a newer cycle`; the superseding cycle owns the gate |
| Second push inside one cycle | Refused: `push already consumed for this snapshot`; the batch is exactly one authorized write set |
| Host seam unbound (unified graph active, transport nil) | Round skips with `userDataSyncStatus = unavailable("family sync host seam is not bound")`; never falls back to an unfenced writer |
| Legacy graph (`foodJournalRuntime == nil`) | Families inactive by design; privacy copy stays local-only |
| Journal store unreadable / corrupt row | Family throws; no tombstones pushed (a partial export never masquerades as deletions) |
| Goals store corrupt | Round skips; corrupt goals never sync as "empty" |
| Media referenced but bytes absent after restore | Entry renders without media (same as a locally missing file) |
