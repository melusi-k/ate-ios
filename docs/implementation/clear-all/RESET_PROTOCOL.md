# Clear all implementation boundaries

Candidate base: main 2ff1aa8e2a0cb0c510c69959d0a242b678754043. No production mutation or call sites. Swift and SQL not compiled/executed in a native/database environment.

## Scope grounded in user decision

Account-wide app-data reset, not account or subscription cancellation. Recipes and Shopping have cloud rows. Journal/Food Journal, media, history, preferences, diary and goals are local. An account reset generation must tell each device to clear those local copies when it reconnects. Cannot promise instant physical erasure from an offline/unreachable device. Current local Journal is NOT owner-scoped, so cannot target one account's Journal without clearing the device-wide journal. User's full clear on the initiating device supports this; clearing unrelated users' local Journal on another shared device remains an ownership boundary requiring product handling.

Public shares, feedback/telemetry, records in Apple Health/Apple Journal, and copies already exported outside ate are outside the reset engine. No public-share/backend logs deletion inferred. UI must not claim every third-party copy gone. Existing migrations/docs are source contracts, not proof of deployed server schema.

## Required protocol before wiring

1. Persist owner ID, request UUID, expected server generation and reset phase in an app-owned control record. Do NOT save personal data as rollback backup. Do not store bearer tokens in this record. Require online session for account reset; signed-out local reset is a separately labelled route, never pretend account clear succeeded.
2. Acquire a durable cross-process gate covering app, extensions/intents, share import, Journal/diary/goals, covers/generation, widget queues, sync, cook/Undo, archive recovery and startup. Current app has no complete gate. Cancel tasks AND invalidate their captured generation. Check generation/owner after each await before effects; cancellation alone is insufficient.
3. Cancel stale Shopping Undo batches/toast closures, draft/edit/add forms, pending imports/search/navigation and generator completions. Existing persisted UI settings must reset their in-memory models too, or didSet can recreate deleted keys.
4. Obtain consistent account snapshot. If local captured generation mismatches, do NOT re-label old local rows with new generation. Clear old content first, discard queued work and start empty. Treat old clients as blocked-for-update after reset; they must not get permission to mutate new generation by inferred defaults.
5. Invoke clear_account_data with persisted request UUID/expected generation. RPC atomically increments generation and deletes ALL owner cloud rows including remote-only rows, independent of client timestamps. Every insert/update is generation-fenced under the same state row lock. New owner write after reset with fresh generation is legitimate new content, not a reset failure. Old requests cannot revive old data.
6. If response is lost, retry exact request. Never issue a fresh reset UUID automatically. A stale retry after a later reset is rejected by expected generation. Require owner binding and detect account switch at every phase. Persist returned generation before allowing writes.
7. Erase all local stores and retained copies, including invalid/undecodable rows, orphan payloads and media. No backup-for-undo. Verify each component independently. On failure keep gate and durable pending state, report components still uncleared, retry idempotently. Cloud committed + local failure must say exactly that, not success or rollback.
8. Reset all in-memory state and derived surfaces. Await notification removal/Live Activity ends/Spotlight deletion; cancel delayed index/publish tasks, invalidate CoverStore caches/tasks and write verified empty shared snapshots. Empty cached snapshot must not skip forced publish because lastPublished matches. Flush queues only under extension writer gate.
9. PhoneWatchBridge must carry reset generation and request; WatchStore must invalidate stale refresh/toggle completions and remove cache/timers/cook mirrors on mismatch before fetch. Verify acknowledgements for reachable paired Watch, report pending other devices. Account generation is enforced server-side regardless of local/offline delivery. No fiction that immediate remote physical erase is possible.
10. Verify all required components and cloud generation receipt; release writer gate only after successful local completion. On relaunch resume pending erase BEFORE migration/recovery/seeding/sync/widget queues. Keep non-personal reset receipt/generation control state required to prevent resurrection, not zero every key indiscriminately.

## Required verification

Owned ephemeral two-account Postgres database: generation-0 legacy write pre-reset allowed; same after reset rejected; reset account A does not affect B; direct state mutation denied; owner spoof rejected; remote-only rows gone; concurrent old upsert/reset serialized in either order; same UUID retry idempotent; stale first request after second reset rejected; snapshot generation+rows consistent. New-generation write survives retry of same reset. Actor-authz/RLS tested under actual authenticated role. No local Postgres server/native Swift toolchain found here; test execution pending.

Native fixture tests: all raw rows/media/defaults/queues/backups gone after relaunch; injected failures retain accurate partial state and retry; nil/unavailable store is a failure, not empty; stale async completions and Undo/Watch writes rejected; corrupt/future rows cleared; account switch cannot erase wrong owner's data; no account/subscription/public-share mutations. Actual UI confirmation/helper placement and empty states require retained screenshots. Candidate tests are written, not pass claims.

Database concurrency note: PostgreSQL may detect a deadlock between a row UPDATE already holding a row lock and the reset state lock. Aborting one transaction is safe, but the client must retry the SAME reset request after deadlock/serialization errors. A proposed migration is not a deployed schema claim. Full all-device Journal erasure needs a reset-aware client update and an ownership-safe policy for shared devices; existing legacy clients cannot do it.
